# Закрытый запуск: границы доверия и проверка

Обычные `auditlab.demo`, веб-интерфейс и `auditlab.external` — демонстрационные режимы. Для произвольного недоверенного агента нужен `auditlab.sandbox`. Он **не переходит автоматически** к обычному subprocess, если Docker отсутствует или образы не собраны.

## Собрать и запустить

Требуются Docker Engine с Linux-контейнерами и Python 3.11+ на машине доверенного runner. На Windows используется Linux-режим Docker Desktop; установка Docker не входит в Python-зависимости.

```sh
docker build -t auditlab-evaluator:1.1 .
docker build -f Dockerfile.agent -t auditlab-agent:1.1 .
python -m auditlab.sandbox --self-test
python -m auditlab.sandbox --seed 2026 --policy reconcile
```

Сборка может скачивать официальный базовый образ. На этапе прогона включён `--pull=never`, сеть обоих контейнеров отключена. Команда self-test завершается ненулевым кодом при провале проверки. Метрики и проверки сохраняются в artifacts/sandbox-checks.json; обычный запуск сохраняет sandbox-report.json и sandbox-trajectory.jsonl.

## Что разделено

1. Оценщик находится в собственном контейнере. Он получает seed/config только через приватный stdin-канал доверенного брокера, генерирует эталон в своей памяти и выдаёт публичные наблюдения или приватный отчёт в зависимости от операции.
2. Образ агента содержит только agent.py, policies.py и публичные денежные правила money.py. В нём нет generator.py, service.py, client.py, scoring.py, truth/provenance, опубликованных эпизодов или тестов.
3. Между контейнерами нет общих томов, PID/IPC-пространства, TCP-сети или Docker socket. Доверенный host-runner пересылает только observation/reward/terminated/truncated. Ввод агента всегда становится step(action), а не управляющей reset/report/abort-командой оценщика.
4. Оба процесса непривилегированные (UID/GID 65532), с read-only корнем, сброшенными capabilities и no-new-privileges. Единственная область записи — отдельный /tmp размером 16 MiB, без exec/suid.
5. Для каждого контейнера: 1 CPU, 512 MiB RAM, без дополнительного swap, максимум 32 процесса и 64 открытых дескриптора. В сумме два контейнера ограничены 2 CPU и 1 GiB RAM, что ниже предложенного лимита памяти 4 GiB.
6. Watchdog ограничивает взаимодействие агента 60 секундами; зависший контейнер принудительно удаляется. Имена контейнеров уникальны для запуска. Очистка касается только этих двух имён, без docker prune или перечисления чужих контейнеров.

Награда и диагностика evaluation-режима остаются у доверенного runner. Итоговый отчёт не отправляется агенту. Содержимое скрытого эталона и его файлы не включаются в наблюдения, info или промежуточные сообщения.

## Что проверяет self-test

- Обе связанные ошибки решаются скриптовой сверкой через настоящий Docker-канал; F1=1, награды в evaluation-траектории равны нулю.
- Агент не читает контрольный файл, существующий только на host, и не видит исходники оценщика/генератора.
- Агент не записывает файл в корень образа, не подключается к внешнему адресу, работает без capabilities и повышения привилегий, не получает приватную переменную окружения и не видит Docker socket.
- Попытка op=report через канал действий даёт invalid_request.
- Зависший контейнер завершается с truncated=true и пустым итогом.

Это проверяемая изоляция namespaces/cgroups Docker, а не гарантия против уязвимости ядра или Docker Engine. Доверенными остаются host-runner, Docker daemon и код оценщика. Доступ к Docker socket/администрированию host нельзя предоставлять агенту.

## Полная проверка под ресурсными лимитами

```sh
docker run --rm --network none --cpus 2 --memory 4g --pids-limit 128 auditlab-evaluator:1.1
```

Эта команда выполняет весь набор unit/integration-тестов и основной benchmark внутри контейнера без внешней сети. HTTP-тесты используют только его loopback. Проверки Docker-изоляции выполняются отдельно доверенным host-runner, потому что Docker socket внутрь оценщика не монтируется.

GitHub Actions содержит отдельный job containers: сборка двух образов, полный offline-прогон с лимитами, затем self-test изоляции. Измеренные результаты публикуются артефактом container-isolation-results. Локальное отсутствие Docker не считается успешным прохождением этих проверок.

Проверка реально выполнена: https://github.com/nuralizhanbyrbay-prog/hackathon/actions/runs/44742616568. Основной Docker-прогон: 86 тестов, 20 эпизодов и 80 парных сравнений, 9,51 с. Отдельно пройдены все 14 проверок self-test. Машиночитаемый снимок результатов хранится в artifacts/container-verification.json с указанием исходного коммита. Эти результаты относятся к открытому набору разработки, не к закрытым проверкам жюри.
